# 长文档核验：先降低可避免的二次重审

**我的选择：先做按小组限定的底稿同步前置分流试点。** 核验前计算底稿同步间隔，制造、消费、科技、金融组超过 **15 分钟**时先核对版本、同步后重新核验。医疗组暂不适用此规则。所有记录保留律师审查，不把“未标记”当作“核验合格”。

后两天时间留出回放中，规则标记 **74/346 条（21.4%）**，覆盖历史失效 **24/33 条（72.7%）**，同时误标 50 条、漏标失效 9 条。**如果**同步能消除其中一半失效，按题目工时口径测算净减少 **700 工时（17.7%）**。这是试点假设，**不是已实现的节省或准确率提升**。

## 1. 我的判断

### 先把统计口径做对

唯一数据来源是题目发放的 [verification_logs.csv](data/verification_logs.csv)，按字节原样保存。无外部数据，无补造业务记录。

|核对项|结果|处理|
|---|---:|---|
|原始数据行（不含表头）|1,214|保留原件|
|完全重复的多余行|58|所有字段完全相同才去重|
|独立 item_id|1,156|同 ID 内容冲突则报错，不擅自选版本|
|核验结果缺失|52|保留为待追踪，不能当通过或失效|
|可用于效果分析的记录|1,104|其中失效 120，通过 984|
|失效率|10.87%|120 / 1,104|
|观察时间|2026-09-01 至 2026-09-07|统一为东八区|
|同步间隔|0–65 分钟|按带时区时间戳相减|

`check_time` 带 `+08:00`，`doc_synced_at` 使用 `Z`（UTC）；不能把文本时分直接相减得出“滞后八小时”。原始文件 SHA-256：`deb9315f42e576e7227b98ec81ee5f34294d00bc5c3ab4d9bad0a43b7d460822`。

### 同步间隔是主要风险线索，但小组之间不同

|同步间隔|有标签数|失效|失效率|
|---|---:|---:|---:|
|≤15 分钟|776|23|2.96%|
|>15 分钟|328|97|29.57%|

超时组失效率约为另一组 **9.98 倍**，包含全部已知失效的 **80.8%（97/120）**。在 10 类条款内分别比较，超时组失效率均较高，说明不能仅凭“历史沿革失效率最高”就先做条款专项模型。详见 [分层结果](reports/stratified_lag.csv)。

**关键例外是医疗组：** 超时记录失效率为 4/69（5.80%），未超时为 14/160（8.75%），方向相反。前五天对医疗组标记 50 条、只命中 4 条失效；即便 100% 修复，`4×120−50×10=−20` 工时，故训练阶段就排除医疗组。其他四组纳入试点。消费组后两天只有 2 条失效，试点情景收益为 −50 工时，提醒我们整体收益不保证每组、每天都获益，必须分组监控。

**根问题判断：** 当前流程缺少经验证的“核验输入是否适合直接比对”的前置分流。底稿新鲜度是主要风险线索，医疗组还有不同的失效机制。数据只能支持关联及排序，无法证明同步滞后导致失效。没有原文、文档版本、失败原因、同步后复核结果，不能断言模型能力不足或承诺同步修复。

另一个待调查信号：医疗组未超时的 14 条失效中，13 条相似度≤3；该层低分记录共 27 条。先核查证据定位、评分含义与样本标签，不能把低分自动归因为底稿不同步，更不能直接把这 27 条计作同步收益。全量分数只有 0–30，未经校准，不解释为概率。Token 是本次处理的事后消耗，不能作为核验前拦截条件。

## 2. 做了什么

1. **可复现审计与诊断**：标准库 Python 处理完全重复、缺标签、混合时区，输出按同步间隔、小组、条款、日期、分数和 Token 的统计及逐条计算结果。
2. **冻结可解释规则**：前五天选择同步阈值，再以训练数据筛选适用小组，导出 [policy.json](reports/policy.json)。规则只使用两个时间字段和小组，不读取结果标签、相似度或 Token。
3. **给业务的清单**：[sync_queue.csv](reports/sync_queue.csv) 为这批历史数据回放产生的 **274 条**候选同步记录，其中 **15 条**缺标签；[missing_label_queue.csv](reports/missing_label_queue.csv) 是全部 **52 条**缺标签追踪清单。它们不是今天待办或已经执行的任务。不要对已发生记录重复核验并宣称产生了节省。
4. **可运行分流工具**：[triage.py](triage.py) 可将冻结规则应用到新数据，输出 `WAIT_SYNC` / `CONTINUE_CHECK` / `REVIEW_TIME_ERROR` / `REVIEW_TEAM_ERROR`。时间异常需人工核对，未纳入试点的小组继续原流程。

先做风险分流能直接改变核验顺序，且易于回退；仅做看板无法降低重审，复杂分类器无法解决“同步是否能修复”的证据缺口。这里没有修改模型，也没有宣称解决全部失效。

## 3. 怎么证明有用

### 时间回放协议

- **校准窗口：9 月 1–5 日**，758 条有标签记录，87 条失效。
- **回放窗口：9 月 6–7 日**，346 条有标签记录，33 条失效。
- 先去重再按东八区日历划分，同一 `item_id` 不跨窗口。缺标签记录不参与选择或收益估计。
- 候选阈值为 `0,5,…,65,90` 分钟。在前五天最大化 `120×0.5×命中失效数−10×标记数`，同收益优先较少标记，再选较小阈值。结果为 `>15 分钟`。[训练搜索明细](reports/threshold_search_train.csv)。
- 固定上述阈值后，小组训练期标记数至少 30 且同一收益公式严格为正才纳入。这是人为设计的保守样本门槛，不是统计显著性结论。[小组选择明细](reports/team_eligibility_train.csv)。
- **诚实边界：初始探索已查看全量分组。** 这是探索后的时间留出回放，不能称为从未接触过的盲测。阈值和小组选择只读取前五天，但仍需新数据前瞻验证，不能把两天样本外推成年收益。

|窗口|有标签|失效|标记|命中失效|误标（原本通过）|漏标失效|q=50%情景净工时|
|---|---:|---:|---:|---:|---:|---:|---:|
|前五天校准|758|87|185|69|116|18|2,290|
|后两天回放|346|33|74|24|50|9|700|
|全周描述性汇总|1,104|120|259|93|166|27|2,990|

回放期命中率 `24/74=32.4%`，失效覆盖率 `24/33=72.7%`。**命中失效只表示找到了风险，不能当作已经修复。** 在 q=50% 情景下预期避免的是 12 次失效，而非 24 次。

### 用同一成本口径比较方案

以下均为后两天 346 条有标签记录；低分≤3 为探索性基线，分数可用时点未获验证。

|方案|标记|命中失效|误标|漏标失效|q=50%情景净工时|
|---|---:|---:|---:|---:|---:|
|原流程，不分流|0|0|0|33|0|
|全部标记待同步|346|33|313|0|−1,480|
|统一 >15 分钟|93|24|69|9|510|
|**按小组限定 >15 分钟（本方案）**|**74**|**24**|**50**|**9**|**700**|
|仅低分≤3|47|8|39|25|10|
|统一超时或低分≤3|128|29|99|4|460|

全部待同步在该情景反而增加工时。本方案比统一超时规则少打扰 19 条正常记录，保留相同失效覆盖。完整结果见 [strategy_comparison.csv](reports/strategy_comparison.csv)。

### 收益依赖修复率，必须把假设公开

题目给定每次失效损失约 **120 工时**、每次提前标记约 **10 工时**，照此计算，不擅自改成分钟。设 `q` 为被命中历史失效中通过同步真正避免重审的比例：

```text
基线工时 = 120 × 全部失效数
净减少工时 = 120 × q × 命中失效数 − 10 × 所有标记数
干预后期望工时 = 基线工时 − 净减少工时
```

后两天基线为 `33×120=3,960` 工时：

|假设修复率 q|预期避免失效次数|净减少工时|
|---|---:|---:|
|0%|0|−740|
|25%|6|−20|
|50%|12|700|
|75%|18|1,420|
|100%（模型内上界）|24|2,140|

盈亏平衡点为 `740/(24×120)=25.7%`。**q=50% 是场景假设，不是日志估计的概率。** 10 工时假设覆盖一次标记及题目指定的前置处理；额外同步、再次调用模型、排队等待或标记导致新错误的成本没有数据，如存在应再扣除。回放收益只涵盖有标签记录，不能免费忽略部署中缺标签标记的成本。

完整数据有 52 条缺标签：原始超时组为 17/345，未超时组为 35/811。缺失可能非随机，不能默认它们具有相同失效率；先补全结果，再更新收益。

后两天另外有 **2 条**无标签记录会被标记，因此完整候选流量是 **76 条**。固定 q=50% 时，假设这2条原本都不失效，额外扣20工时后净收益为 **680 工时**；假设它们原本都失效则为 **800 工时**。这是缺标签状态的情景范围，不是置信区间；已知标签也不能保证无标注误差。[缺标签边界计算](reports/missing_label_bounds.csv)。

### 上线前验证业务闭环

先影子运行并由律师确认失效原因；只在四个适用组小规模做受控试点，同组同条款随机分配“原流程”与“版本核对＋同步后核验”，两边保留相同最终审查标准。新采集原版本/新版本标识、同步是否产生更新、首次失效原因、同步后有效性、实际处理与等待工时。

主要指标是每条核验的**总实际审查工时**和律师最终确认的有效性，辅助指标为二次重审率、标记量、同步后修复率、交付耗时，按小组/条款分层。只有前瞻数据确认净工时改善且最终有效性不下降才扩大。消费组单独监控，医疗组先查低分失效；无证据不扩大同步拦截。出现交付准确率下降或工时恶化就回退。样本量与观察周期需按未来量级及可接受差异制定，本数据不足以承诺周期。

## 4. 复现与使用

需要 **Python 3.10+**，无第三方依赖，无需联网或 API 密钥。在仓根执行：

```bash
python3 analyze.py
python3 -m unittest discover -s tests -v
```

重建 `reports/` 内全部分析结果。更换输入或独立输出目录：

```bash
python3 analyze.py --input data/verification_logs.csv --out /tmp/verification-report
```

验证结果：**9 项单元测试通过**；原始文件与发放文件逐字节一致；在独立目录重建的全部报告逐字节一致；分流 CLI 的 1,156 条行动与逐条分析输出一致。

对业务 CSV 使用冻结规则（至少包含 `item_id,check_time,doc_synced_at,team_code`，无需结果标签）：

```bash
python3 triage.py reports/records.csv --out /tmp/triage-result.csv
```

以上是本批历史数据的演示；新数据替换第一个参数。分流工具不会重新拟合阈值；`analyze.py` 会重新校准，仅用于离线分析。未知小组不自动纳入试点。测试中的时间与异常输入属于明确标记的合成测试夹具，不进入业务结论。
